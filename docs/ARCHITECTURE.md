# Архитектура foto2word

## Задача

foto2word преобразует фотографию бумажного документа в редактируемый DOCX. Система должна
сохранить исходный текст, структуру, таблицы, изображения и отмеченные от руки исправления,
а затем дать пользователю проверить результат перед скачиванием.

Модель отвечает за понимание изображения и возвращает строго типизированный `DocModel`.
Формирование DOCX, проверка обязательных значений и применение исправлений выполняются
обычным детерминированным кодом.

## Слои

Зависимости направлены от внешних деталей к внутренним правилам:

```text
web / cli
    |
composition
    |
infrastructure -> application -> domain
```

### Domain

`src/foto2word/domain` содержит модели документа, блоков, исправлений, изображений, профилей
оформления и ошибок валидации. Этот слой не знает об HTTP, конкретных AI-провайдерах,
файловой системе и способе формирования DOCX.

### Application

`src/foto2word/application` описывает сценарии преобразования, проверки, повторного просмотра
и пользовательских сессий. Внешние зависимости представлены протоколами в `ports.py`
и `sessions.py`:

- `VisionModel`
- `DocumentReviewer`
- `DocumentRenderer`
- `Previewer`
- `SecondReader`
- `SessionStore`

Сценарии получают реализации через конструкторы. Благодаря этому тесты используют локальные
заглушки и не обращаются к внешним API.

### Infrastructure

`src/foto2word/infrastructure` содержит заменяемые технические реализации:

- адаптеры OpenAI, Anthropic и OpenAI-compatible API
- импорт и формирование DOCX
- OCR через Windows и Yandex Vision
- чтение PDF и таблиц
- формирование превью через Word или LibreOffice
- хранение пользовательских сессий
- загрузку профилей оформления из YAML

Общая логика структурированного ответа находится в базовом классе провайдера. Конкретные
адаптеры отвечают только за формат запроса, передачу изображения и разбор ответа API.

### Composition

`composition.py` является корнем сборки зависимостей. Только этот модуль выбирает конкретный
AI-провайдер, OCR, renderer, previewer и session store на основании конфигурации.

### Interfaces

`cli` и `web` являются тонкими входными слоями. Они проверяют ввод, вызывают application-сценарии
и преобразуют результат в CLI-вывод или HTTP-ответ. Бизнес-правила не размещаются в обработчиках.

`frontend/src` содержит разделённый по ответственностям интерфейс Copeeq v5. Сборка
объединяет ES-модули и HTML-шаблоны в `web/copeeq`. Сейчас интерфейс работает как независимый мокап с локальными
демонстрационными данными. Он не вызывает API foto2word и не требует ключа AI-провайдера.
Подключение к application API отложено; backend и его тесты сохранены отдельно.

### Устройство интерфейса

- `domain/` содержит правила стоимости, списания кредитов, фабрику документа и план демообработки.
  Эти классы не зависят от DOM, React и состояния интерфейса.
- `controllers/` разделяет загрузку, обработку, документы, редактирование, просмотр, подпись,
  авторизацию, оплату и представления отдельных экранов. Блоки лендинга имеют свои представления.
- `composition.js` создаёт классы и передаёт необходимые функции через порты. Контроллеры
  не импортируют другие контроллеры и не получают доступ к общему реестру сервисов.
- `application.js` выбирает представление маршрута и модального окна, управляет жизненным циклом.
- `infrastructure/` связывает состояние с runtime и управляет DOM-ссылками и таймерами.
  При уничтожении приложения отменяются таймеры всех функций и снимаются обработчики событий.
- `templates/screens/`, `templates/layout/` и `styles/` содержат исходную вёрстку по экранам и блокам.
- `public/` хранит изображения, исходные иконки, документ DocSheet и сгенерированный runtime.

`index.js` является тонким адаптером рендеринга. В нём нет загрузки файлов, платежей,
редактирования документа и расчёта стоимости. Один итоговый браузерный bundle является
результатом сборки; исходники и обязанности остаются разделёнными.

Команды проверки интерфейса: `npm run lint --prefix frontend`,
`npm run format:check --prefix frontend`, `npm test --prefix frontend`.

## Конвейер преобразования

```text
Фото
  -> нормализация изображения
  -> структурированное распознавание в DocModel
  -> проверка модели документа
  -> детерминированная сборка DOCX
  -> независимая сверка значимых полей
  -> опциональный визуальный review
  -> пользовательская проверка
  -> экспорт
```

Результат модели не записывается напрямую в DOCX. Сначала он проходит Pydantic-валидацию и
проверки доменного слоя. Это ограничивает свободный текст модели и делает ошибки наблюдаемыми.

## Расширение системы

Новый AI-провайдер реализует базовый контракт в `infrastructure/providers` и регистрируется в
`composition.PROVIDERS`. Application-слой при этом не изменяется.

Новый тип документа добавляется YAML-профилем в `profiles`. Новый тип блока требует доменной
модели, поддержки в renderer и отображения в синтетическом rasterizer.

## Проверка качества

Проект разделяет два вида проверки:

1. Автоматические тесты проверяют код, контракты, рендеринг, импорт и обработку ошибок без сети.
2. Eval-наборы сравнивают ответы провайдеров с проверенным `expected.docmodel.json` и считают
   метрики текста, структуры, полей и исправлений.

Реальные eval-наборы не входят в публичный репозиторий, потому что документы могут содержать
персональные данные. Формат набора описан в `evals/README.md`.

## Ограничения

- Качество зависит от выбранной vision-модели и качества фотографии.
- Результат с важными персональными или финансовыми данными требует проверки человеком.
- Для визуального сравнения нужен Microsoft Word на Windows или LibreOffice.
- Подключение внешнего провайдера может означать передачу ему содержимого документа.

Проект не заявляет юридическую или абсолютную точность распознавания. Его задача состоит в том,
чтобы сделать результат редактируемым, проверяемым и воспроизводимым.
